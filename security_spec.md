# Security Specification — Dyeing & Washing Mill Ledger

## 1. Data Invariants
1. **No Stored Balance**: `/clients/{clientId}` strictly forbids a `balance` or `currentDue` field. Only `ownerId`, `clientName`, `companyName`, `mobile`, `address`, `createdAt`, and `updatedAt` are allowed.
2. **Strict Ownership & PII Isolation**: Client profiles contain PII (`mobile`, `address`). Both `get` and `list` operations on `/clients`, `/client_ledger`, and `/orders` strictly require an authenticated, email-verified user (`request.auth.token.email_verified == true`) whose `request.auth.uid == resource.data.ownerId`.
3. **Referential & Atomic Integrity**: Every `/client_ledger/{entryId}` created MUST reference an existing (or atomically batch-created) `/clients/{clientId}` owned by `request.auth.uid`. Every `/orders/{orderId}` created MUST reference an existing `/clients/{clientId}` owned by `request.auth.uid`.
4. **Immutable Append-Only Ledger**: Entries in `/client_ledger/{entryId}` are append-only (`allow update, delete: if false`).
5. **Order Terminal State Locking & Atomic Auto-Billing**:
   - Orders cannot be created directly in `"Delivered"` status (`finalGaj`, `finalBillAmount`, and `deliveredAt` must be `null` on create).
   - Once `existing().status == "Delivered"`, the order is locked permanently against any subsequent updates (`existing().status != "Delivered"`).
   - Transitioning an order to `"Delivered"` MUST occur in an atomic batch alongside `/client_ledger/INV_{orderId}` where `txn_type == "invoice"`, `debit == finalBillAmount`, `credit == 0`, `reference == orderId`, and `abs(finalBillAmount - (finalGaj * rate)) <= 0.02`.
6. **Temporal & ID Integrity**: `createdAt`, `updatedAt`, and `deliveredAt` must equal `request.time`. All document IDs match `^[a-zA-Z0-9_\-]+$` (max 128 chars).
7. **Atomic Client Payment & Cash Flow Integrity**: Every `/money_in/{paymentId}` document is append-only (`allow update, delete: if false`), enforces `reference == paymentId` matching `^PAY-[a-zA-Z0-9_\-]+$`, restricts `paymentMethod` to `Cash` | `Bank` | `Mobile Banking`, and verifies via `existsAfter` / `getAfter` that `/client_ledger/{paymentId}` exists in the same atomic batch with `txn_type == "payment"`, `debit == 0`, `credit == amount`, and matching `clientId`.
8. **Inverted Append-Only Supplier Payable Ledger**: `/suppliers/{supplierId}` forbids stored payable/balance fields. `/supplier_ledger/{entryId}` is append-only (`allow update, delete: if false`) with inverted payable signs: `opening` and `purchase` require `credit > 0 && debit == 0`, while `payment` requires `debit > 0 && credit == 0`. Total Payable is dynamically computed as `(Sum of Credit) - (Sum of Debit)`.
9. **Atomic Purchase & Supplier Payment Outflow**: `/purchases/{purchaseId}` verifies `abs(totalAmount - quantity * rate) <= 0.02` and enforces atomic creation of `/supplier_ledger/{purchaseId}` (`txn_type == "purchase"`, `credit == totalAmount`, `debit == 0`). `/money_out/{paymentId}` is append-only, restricts `paymentMethod` to `Cash` | `Bank`, and for supplier payments (`SPAY-*`) enforces atomic creation of `/supplier_ledger/{paymentId}` (`txn_type == "payment"`, `debit == amount`, `credit == 0`).
10. **Atomic Factory Expense & Cash Outflow Integrity**: `/expenses/{expenseId}` is append-only (`allow update, delete: if false`), restricts `category` to `Salary` | `Electricity` | `Rent` | `Transport` | `Maintenance` | `Food` | `Office` | `Other`, restricts `paymentMethod` to `Cash` | `Bank`, enforces `reference == expenseId` matching `^EXP-[a-zA-Z0-9_\-]+$`, and requires bidirectional atomic creation (`existsAfter` / `getAfter`) of `/money_out/{expenseId}` with identical `ownerId`, `reference`, `category`, `amount`, `paymentDate == expenseDate`, and `paymentMethod`.
11. **Inventory Stock Bounds & Atomic Movement Integrity**: `/inventory/{itemId}` enforces non-negative bounded `currentStock` and `minStockLevel`, restricts `unit` to `KG` | `Liter` | `Pcs`, locks `itemName`/`unit`/`ownerId`/`createdAt` after creation, and only permits action-based updates to `['currentStock', 'updatedAt']` or `['minStockLevel', 'updatedAt']`. `/stock_movements/{movementId}` is append-only (`allow update, delete: if false`), verifies arithmetic consistency (`opening`, `in`/`purchase`, `out`), and enforces via `existsAfter` / `getAfter` that the parent `/inventory/{inventoryItemId}` exists, belongs to `request.auth.uid`, has a matching `unit`, and ends with `currentStock == resultingStock`.
12. **Employee PII Isolation & Atomic Weekly Advance Outflow Integrity**: `/employees/{employeeId}` stores PII (`mobile`, `basicSalary`) and is strictly restricted to `admin`. `/employee_advances/{advanceId}` is restricted to `admin`, enforces `reference == advanceId` matching `^ADV-[a-zA-Z0-9_\-]+$`, verifies that `/employees/{employeeId}` exists, requires bidirectional atomic creation (`existsAfter` / `getAfter`) of `/money_out/{advanceId}` with `category == "Employee Advance"`, and allows `update` ONLY for the one-way terminal deduction lock (`deducted: true`, `deductedBySalaryId`, `deductedAt == request.time`) verified against an atomically created `/salary_payments/{deductedBySalaryId}` for the same employee.
13. **Role-Based Access Control (RBAC) & First User Lock**:
    - `/users/{userId}` stores `uid`, `email`, `displayName`, `role` (`admin` | `manager` | `accountant`), `createdAt`, `updatedAt`. `get` is strictly restricted to `request.auth.uid == userId || isAdmin()`. `list` and role `update` are strictly restricted to `isAdmin()`.
    - First User Rule: Creating `/users/{uid}` with `role == "admin"` is ONLY permitted if `isBootstrappedAdmin()` (verified runtime admin email) OR atomically paired with creating the immutable singleton `/app_meta/bootstrap` when it does not yet exist. All subsequent users MUST register with `role == "manager"` and CANNOT elevate their own role.
    - Role Enforcement across Collections:
      - `money_in`, `money_out`, `expenses`: strictly `admin` and `accountant`.
      - `orders`, `purchases`, `inventory`, `stock_movements`: strictly `admin` and `manager`.
      - `employees`, `employee_advances`, `salary_payments`, `users` list/role updates: strictly `admin`.
      - Master Data edits/deletes (`clients`, `suppliers`, `inventory`, `employees`) and pending/processing transaction edits/deletes (`orders`, `purchases`): strictly `admin`.
14. **Atomic Monthly Salary Payment & Double-Deduction Prevention**: `/salary_payments/{salaryId}` is append-only (`allow update, delete: if false`), strictly restricted to `admin`, enforces `reference == salaryId` matching `^SAL-[a-zA-Z0-9_\-]+$`, verifies arithmetic `abs(netSalary - (basicSalary + overtimeAmount + bonusAmount - advanceDeduction)) <= 0.02`, verifies `/employees/{employeeId}` exists, and when `netSalary > 0` requires bidirectional atomic creation (`existsAfter` / `getAfter`) of `/money_out/{salaryId}` with `category == "Salary"`, `reference == salaryId`, `salaryPaymentId == salaryId`, and `amount == netSalary`. Deducted advances are locked via `deducted == true` and cannot be reverted to `false` or re-deducted.

## 2. Adversarial Payloads (Must All Return PERMISSION_DENIED)
1. **Unauthenticated Read/Write** on `/users`, `/app_meta`, `/clients`, `/client_ledger`, `/orders`, `/expenses`, `/money_in`, `/money_out`, `/inventory`, `/stock_movements`, `/employees`, `/employee_advances`, or `/salary_payments`.
2. **Unverified Email Spoofing** (`email_verified == false`, even with admin email).
3. **Self-Assigned Admin Escalation** (a second user creating `/users/{uid}` with `role: "admin"` after `/app_meta/bootstrap` already exists, or a manager updating their own `/users/{uid}` `role` field to `"admin"`).
4. **Non-Admin User Directory PII Read** (Manager or Accountant attempting `get` on another user's `/users/{otherUid}` or `list` on `/users`).
5. **Manager Writing Cash Collections** (Manager attempting `create` or `read` on `/money_in`, `/money_out`, or `/expenses`).
6. **Accountant Accessing Operations/Inventory/Payroll** (Accountant attempting `read` or `write` on `/orders`, `/purchases`, `/inventory`, `/stock_movements`, `/employees`, `/employee_advances`, or `/salary_payments`).
7. **Non-Admin Master Data Edit/Delete** (Manager or Accountant attempting `update` or `delete` on `/clients`, `/suppliers`, `/orders` details, `/purchases` details, `/inventory` metadata, or `/employees`).
8. **Identity Spoofing on Create** (`ownerId != request.auth.uid` or `users/{uid}` where `data.uid != request.auth.uid`).
9. **Shadow Field Injection** (`balance` on `/clients`, `isSuperAdmin: true` on `/users`, or extra fields on any entity).
10. **ID Poisoning & Backdated Timestamps** (`bad$id with spaces`, > 128 chars, or `createdAt != request.time`).
11. **Bootstrap Tampering** (updating or deleting `/app_meta/bootstrap` or creating `/app_meta/other`).
12. **Terminal State / Immutable Ledger Tampering** (updating a `Delivered` order or `Paid` purchase, mutating/deleting `client_ledger`, `supplier_ledger`, `money_in`, `money_out`, `expenses`, `stock_movements`, or `salary_payments`, or reverting an already-deducted `employee_advances` document).
13. **Payroll Forgery & Non-Atomic Salary Payout** (forged `netSalary` mismatching `basicSalary + overtimeAmount + bonusAmount - advanceDeduction`, orphaned `SAL-*` `salary_payments` without atomic `money_out`, or marking an advance `deducted: true` without an atomic `salary_payments` document).
